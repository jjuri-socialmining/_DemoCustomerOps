RAGOps — RAG Pipeline Engineering Evidence

RAGOps is a private workshop repository holding a retrieval-augmented generation pipeline built by hand in Python over a private knowledge base of 25 repositories (~35k markdown documents, ~14.8M words, mostly Spanish, under active development — 2,684 commits across those repositories in 2026 so far): census → chunking → embeddings → vector index → CLI query with source citations. Every number on this page was reproduced by running the script twice before being written down — a non-reproducible number does not get recorded.

04Design decisions, with their numbers

D-001Census the corpus before deciding anything

Three seed repositories, explicit exclusions (VCS internals, virtualenvs, editor config, and an embedded shared submodule — counting it would census the same corpus twice). The header density (~12 per file) predicted that structure-aware chunking would work — a hypothesis stated up front and tested in D-002.

192 files · 2,318 headers · 190,359 words — two runs, same numbers ✔

D-002Chunking: header-based split wins

Side-by-side comparison on 10 real notes: the structure-aware split produces natural-sized chunks with citable metadata (repo, path, full H1 > H2 > H3 breadcrumb); fixed-size windows cut mid-sentence and can't anchor a citation. Oversized sections (long transcripts) are subdivided while keeping their heading. Bug caught along the way: a suspiciously uniform µ=128 tokens exposed the tokenizer silently truncating at the model's maximum — token counts now use the real tokenizer with truncation disabled.

header-based: 141 chunks · µ323 tok vs fixed-size: 104 · µ480 — VALIDATION OK

D-003Multilingual embedding model + 128-token embed cap

The tutorial default (all-MiniLM-L6-v2, English-trained) ranked the hardest control question at position 96 on a Spanish corpus — discarded by measurement, not theory. Lowering the embed cap to the model's real attention window (128 tokens) stopped truncating the tail of every chunk and moved that question from rank 4 to rank 1. Two separate budgets now exist: 1,200 tokens for structural chunks (reading), 128 for embedding — each with its own measured number.

English model: rank 96 ✖ → multilingual, cap 1200: rank 4 → cap 128: rank 1 ✔ (3/3)

D-004Persistent index on sqlite-vec

One local file, no server, no cloud — at this scale anything bigger is cargo cult; the decision gets revisited with numbers if the corpus grows 100×. Vectors are stored normalized, so L2 order is exactly cosine order with zero extra configuration. Model load (~5–7 s, once per process) and query time (32 ms) are reported separately — averaging them would be lying.

1,970 chunks · 4.9 MB · indexed in 1.1 s · 5/5 at rank 1 · 32 ms average query

D-005Corpus expanded to 24 repositories

127× more competition and the controls didn't leave the top-5. Query time went from 32 to 122 ms: brute-force search over 250k vectors is still comfortably inside budget — an ANN index here would be over-engineering. One legacy repository turned out to hold 65% of the corpus, flagged as a potential noise source to be measured, not guessed at.

33,631 files · 13.0 M words · 249,637 chunks · 518.6 MB · embedded in 334 s

D-006The sensitive repository joins: full coverage

The last repository held legal documents, so it entered with written safeguards: the index is a local derivative kept out of version control, querying is read-only toward the owner, and the source repository remains the single source of truth — the index makes material findable, it never becomes the authority. The payoff: the most useful class of daily question moved from out-of-scope to answerable, with the right sources at ranks 1–2.

35,079 files · 14.77 M words · 265,661 chunks · 559.9 MB · 174 ms avg query · MASTER 5/5

D-007Publication governance

The workshop repository (RAGOps) stays private forever: it operates on real names and paths, and sanitizing a live commit history is fragile — one slip leaks the internal silhouette. Public evidence is curated once, reviewed, into this page: aggregated numbers and decisions — never the corpus, the index, or a single real name. Every publication passes explicit human review before push.

05Honest findings (what the system does not do)

  • Counting is not retrieval: aggregation questions ("how many…?") need a structured source, not semantic search. A paradigm limit, not a bug — declared as its own question class for the evaluation set.
  • Duplicate content wastes top-k slots: one legacy repository stores identical files in two folders; identical pairs showed up side by side in the rankings. Candidate fix: content-hash dedup at index time, to be decided with recall@k.
  • Crumb chunks: sections whose content lives entirely in their subsections leave a chunk that is only a title line. They pass validation but are potential noise — measured in the evaluation set, not pruned for cosmetics.
  • 3–5 control questions validate "by eye" — they cannot compare configurations finely. That's the job of the next stage: a golden set of 30–50 questions scored with recall@k and MRR.
